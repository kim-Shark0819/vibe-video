## 1. 목적

통합계정(730335451955)에서 AI POC 비용을 0 으로 만든다. AI POC 의 개발 환경과 개발·배포 도구를 전부 각 고객사 계정으로 옮긴다.
고객사 계정 비용은 많이 늘어도 된다. 비용을 줄이는 작업이 아니라, **비용이 나는 계정을 옮기는 작업**이다.

## 2. 옮길 것 — "개발"의 범위

- dev 환경: dev EKS, dev 앱, dev Neptune·S3, dev ALB·도메인·인증서
- 개발·배포 도구: GitLab(프로젝트·CI), GitLab Runner, ArgoCD, ECR, 배스천
- 모델 호출(Bedrock 등): dev 앱이 부르는 모델 비용도 고객사 계정에서 난다
- 모듈형 플랫폼 검증 환경

## 3. 고객사 계정마다 최종 모습

1. dev VPC 1개 + dev EKS 1개 (CIDR 는 현황정리 §7 배정안)
2. GitLab + Runner + ArgoCD — 통합계정 구성을 복제한다. 그 고객 코드만 담는다(D-E)
3. 배포: GitLab → ArgoCD → dev EKS 또는 운영 EKS (둘 다 같은 고객사 계정 안)
4. ECR · dev Neptune·S3 · 모델 호출도 그 계정에서

## 4. 운영

1. 운영 EKS 클러스터와 그 안의 앱은 다시 만들거나 옮기지 않는다. 운영 서비스는 끊기면 안 된다.
2. 새 ArgoCD 가 운영 EKS 에 배포하는 데 필요한 **추가** 변경은 이 작업에 포함한다:
   운영 EKS 허용 IP 추가 · access entry 추가 · 운영 이미지를 고객사 ECR 로 전환(같은 이미지 digest).
3. 운영에 닿는 변경은 하나씩 설계자 승인을 받고, 되돌리는 방법을 먼저 문서에 적는다.
4. 기존 통합계정 경로(허용 IP 13.125.117.242 · ArgoCD-CrossAccount-Deployer · 통합계정 ECR)는
   새 경로가 검증되고 설계자 검토가 끝날 때까지 지우지 않는다.
5. 새 ArgoCD 의 운영 첫 동기화는 자동 동기화를 끈 채로 한다. diff 가 이미지 레지스트리 주소 말고는 0 인 것을 보인 뒤 수동으로 동기화한다.

## 5. 순서

고객사 하나씩: **와이낫(파일럿) → 키이스트 → 와이랩 → 이매지너스.**

각 고객사마다:

1. 고객사 계정에 dev 를 구축하고 dev 앱을 배포·검증한다
2. 새 GitLab·ArgoCD 를 그 고객의 운영 EKS 에 연결한다 (승인 후)
3. 설계자가 검토한다
4. 통합계정에서 그 고객 관련 AI POC 자원을 지우고, 운영 쪽 옛 연결을 제거한다 (승인 후)

4곳이 끝나면 통합계정 공용 자원을 지운다(승인 후): ArgoCD · Runner · `AI-POC-eks` · AI-POC VPC(NAT 포함) · 배스천 · ECR · 플랫폼 자원 · D-A 에 따른 것.
이것으로 G1 이 끝난다.
