## 1. 결론

1. Kiro 가 놓친 핵심은 **목적**이다. 지시문에 "통합계정에 AI POC 비용이 남으면 안 된다"가 없었다. 그래서 Kiro 는
   "운영 무접촉"을 최상위 조건으로 삼았고, GitLab·Runner·ArgoCD·ECR·NAT·배스천·AI-POC·플랫폼 검증을
   **통합계정에 남기는** 설계가 나왔다. 빠지는 것은 dev 전용 자원(월 약 $486)뿐이다.
2. Kiro 는 조건 4("운영 EKS 는 그대로")와 조건 3·5("운영 EKS 로 배포", "운영과 연결한 뒤")를 서로 모순으로 읽었다.
   설계자 뜻은 "클러스터는 다시 만들지 않고 서비스는 끊지 않되, 새 ArgoCD 를 연결하는 추가 변경은 한다"로 보인다.
   지시문에 이 구분이 없었다.
3. 가드레일(이매지너스 계정 `726990466389` 에 "STS 외 호출 금지")은 접근 통제가 아니라 **오발 방지**였다는 Kiro 의
   설명은 우리 기록과 맞는다. 다만 원문 세 곳은 이 세션에서 열지 못했다(§5).

## 5. "가드레일 계정" — 왜 생겼나

**무엇.** 이매지너스 운영 계정 `726990466389`(story-ai)에 걸린 규칙이다. "STS(계정 확인) 외 AWS 호출 금지, 프로필을
만들지 않는다." Kiro 는 이것을 "이매지너스 가드레일"이라고 부른다.

### 5.1 경위 (Kiro 인용 + 우리 기록 대조)

| 허브 dev EKS 구축 때 (날짜 확인 필요) | 그때 작업은 `이매지너스/` 폴더 코드를 `AI-POC/` 에 병합하는 것이었고, 그 계정은 필요 없었다. 그런데 그 폴더에 계정 자격증명과 그 계정용 Terraform(eks·neptune·scheduler, tfstate 에는 평문 비밀)이 함께 있었다. `-chdir` 를 한 번만 잘못 써도 남의 운영에 apply 된다. 그래서 "자격증명이 있어도 쓰지 마라 · 다른 계정 접근 금지 · 프로필을 만들지 마라"를 넣었다 | `AI-POC/docs/PRD_AI-POC_DEV-EKS_Terraform.md` §2.2·H4·H7, `tasks.md` 0.2.2 | 원문은 미확인(이 세션은 GitLab 접근 불가) |

### 5.2 판단

- **생긴 이유는 타당했다.** 자격증명과 남의 운영 Terraform 이 한 폴더에 있었고, 그때 작업에는 그 계정이 필요 없었다.
- **문제는 이유가 사라진 뒤에도 남았다는 것이다.** 병합 작업이 끝난 뒤에도 "접근 금지"로 남아 운영 확인을 막았고,
  그래서 "레거시 없음" 오판이 났다.
- **개정안 IM-1~3 은 이관 작업에 맞다.** 다만 IM-2("`story-ai-*` 쓰기 금지")는 Kiro 에게 거는 규칙이고, 설계자의
  `deploy.ps1` 배포는 계속된다는 점을 Kiro 에 알려야 한다. 조건 3 을 이매지너스 운영에도 적용하면 IM-2 와 부딪친다 → 결정 필요(§7 #3).
- **계정번호가 잘못 적혀 있다.** `PRD_modular-platform.md` §4.2 에 이매지너스 계정이 `892278727066` 으로 적혀 있다고 한다.
  이 번호는 **와이랩 운영 계정**이다(9-28 인수인계 §1). 키 조회 결과(`726990466389`)가 맞다. 그 PRD 를 고쳐야 한다.
  틀린 번호를 믿고 작업하면 와이랩 계정에 이매지너스 작업을 하게 된다.
- **보안.** Kiro 대화에 키 3개가 평문으로 들어갔다(현황정리 §4.4). 9-30 의 "노출 키 교체" 대기 건과 합쳐 전부 교체해야 한다.
  고객 계정 작업은 배포용 IAM 역할을 assume 해서 한다.

고객사 계정 비용은 많이 늘어도 된다. 비용을 줄이는 작업이 아니라, 비용이 나는 계정을 옮기는 작업이다.

[옮길 것 — "개발"의 범위]
- dev 환경: dev EKS, dev 앱, dev Neptune·S3, dev ALB·도메인·인증서
